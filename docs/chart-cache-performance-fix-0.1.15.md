# 图表缓存和渲染性能修复（0.1.15）

## 已确认的原因

桌面图表的 DuckDB 缓存使用单条串行操作队列。旧实现对每根 K 线执行一次数据库插入；分时数据每 1000 根通过 IPC 分批写入时，后续批次又会读取、删除并重写之前的全部数据。后台观察列表预热期间，切换到已有缓存的股票也必须等待队列里的写入完成。图表点击处理还在更新选中项前额外读取一次缓存。

另外，策略周期转换对盘前盘后等不属于交易时段的每根分钟线重复解析同一天的交易日和时区。2500 根连续分钟线可使渲染线程在同步计算中停留数秒。

## 修改

- DuckDB 每 250 根使用一条参数化批量 SQL；分时增量批次只更新新增或重复时间戳，不再重写旧分时缓存。日线和周线继续沿用原来的归并规则与原子替换。
- 点击观察列表股票后立即更新选中项，缓存由可取消的页面效果读取；后台预热延后 750 毫秒，以便当前图表先读取缓存。
- 策略周期转换按交易日复用交易时段解析，并复用时区日期格式化器。

## 复测结果与边界

在同一台 Windows 开发机、同样的临时 DuckDB 与 2500 根分时数据上，三批缓存写入由约 7642 毫秒降至约 527 毫秒；排在一个后台 1000 根写入后面的缓存读取由 786–840 毫秒降至 170–184 毫秒。2500 根包含非交易时段的分钟线转换由约 3300 毫秒降至 50–80 毫秒。测试只使用临时数据库，未触碰用户配置或行情缓存；真实用户设备上的绝对耗时仍需安装后验证。

回归测试覆盖 2500 根跨批次缓存、重复时间戳替换和来源摘要，以及跨交易日、盘后、午休的周期归并。`npm test` 与 `npm run check` 通过；桌面端 367 项测试通过。PostgreSQL 集成测试需要独立 `TEST_DATABASE_URL`，本机未配置时由测试套件按既有规则跳过。
